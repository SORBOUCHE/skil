# Automated Patch Verifier (APV) Protocol

## 1. Core Mission & Philosophy

The Automated Patch Verifier (APV) protocol establishes rigorous standards for code modifications generated by autonomous agents. A fix is not merely a change that stops an error message from printing; a genuine fix preserves architectural intent, honors all public and private contracts, introduces zero collateral regressions, and is accompanied by automated regression tests that prevent the defect from recurring.

```
+-------------------------------------------------------------------------------+
|                            The Patch Verification Loop                        |
|                                                                               |
|   [Failing State]                                                             |
|          |                                                                    |
|          v                                                                    |
|   [Root Cause Identified]                                                     |
|          |                                                                    |
|          v                                                                    |
|   [Write Regression Test] -----> Verifies reproduction (RED)                  |
|          |                                                                    |
|          v                                                                    |
|   [Apply Surgical Patch]  -----> Localized, minimal AST change                |
|          |                                                                    |
|          v                                                                    |
|   [Verify Target Test]    -----> Verifies fix resolves defect (GREEN)         |
|          |                                                                    |
|          v                                                                    |
|   [Run Full Test Suite]   -----> Confirms zero regressions across codebase    |
|          |                                                                    |
|          v                                                                    |
|   [Run Static Analysis]   -----> Linter, type check, build validation         |
|          |                                                                    |
|          v                                                                    |
|   [Deployment Ready]                                                          |
+-------------------------------------------------------------------------------+
```

## 2. The Surgical Patch Commandments

1. **Minimal Diff Principle:** Every line of code added or modified increases long-term maintenance overhead. A 3-line targeted patch that solves the root cause is superior to a 50-line speculative refactoring.
2. **Never Weaken Existing Tests:** A failing assertion in an existing test is proof of a broken contract. Changing an assertion from `expect(x).toBe(10)` to `expect(x).toBe(null)` to make tests pass without explicit specification change is strictly prohibited.
3. **Always Add a Regression Test:** If a bug existed, it was because test coverage lacked that specific permutation. A fix without a new regression test is incomplete.
4. **Preserve Public API Contracts:** Function signatures, return types, error codes, and exposed schema structures must remain backwards compatible.

## 3. The 5-Phase Verification Protocol

### Phase 1: Patch Formulation & Diff Minimization
Before writing code, analyze the exact Abstract Syntax Tree (AST) node or logical branch that causes the invariant failure:
- **Locate Target Node:** Identify the specific conditional, assignment, or expression requiring adjustment.
- **Formulate Surgical Replacement:** Construct the minimal code change that restores correct invariant behavior.
- **Review Pre/Post Diff:** Ensure no unrelated formatting changes, unnecessary whitespace changes, or unintended imports are introduced.

### Phase 2: Regression Test Creation (Red Phase)
Before applying the patch to production code:
- Create a test case reproducing the exact failure scenario.
- Execute the test and verify that it **fails** with the expected error signature.
- This confirms the test accurately targets the bug and is not a false positive or trivial pass.

### Phase 3: Patch Application & Target Verification (Green Phase)
Apply the surgical patch to the source file:
- Execute only the targeted regression test.
- Verify that the test transitions from **RED** to **GREEN**.
- Verify that standard logging and metric emissions remain operational.

### Phase 4: Full Suite Regression Pass (Refactor/Sanity Phase)
Run the entire automated verification suite to guarantee zero collateral damage:
- **Unit Tests:** Execute all unit test suites across the repository.
- **Integration Tests:** Verify boundary and database interactions remain consistent.
- **Linter & Style Checks:** Verify zero ESLint, Flake8, Ruff, or Clippy violations.
- **Type Checker:** Run TypeScript compiler (`tsc --noEmit`), `mypy`, or `cargo check` to guarantee type safety.

### Phase 5: Backwards Compatibility Audit
Verify that the change does not break callers:
- Are default argument values preserved?
- Are return shapes strictly compatible with earlier schemas?
- Are errors thrown using domain-compatible exception hierarchies?

## 4. Patch Quality Rubric & Scoring Checklist

Evaluate every generated patch against this scoring checklist:

| Quality Dimension | Criteria for Passing | Failure Indicators |
| :--- | :--- | :--- |
| **Locality** | Touches only relevant functions / files | Edits across 10+ unrelated files |
| **Completeness** | Fixes root cause and handles boundary edges | Patches symptom; crashes on null/empty |
| **Safety** | No silent swallowing of exceptions | Empty `catch {}` or `except: pass` |
| **Test Coverage** | Accompanied by targeted regression test | No new tests added |
| **Formatting** | Matches host project style and linters | Inconsistent indentation, broken lints |
| **Contract Stability** | Backwards compatible parameter shapes | Breaking changes in function signatures |

## 5. Concrete Code Patch Patterns

### Pattern A: Null/Undefined Guard with Sensible Default
**Problem:** Dereferencing an optional property crashes when payload is incomplete.
```typescript
// ❌ Flawed / Anti-pattern Patch (Silencing):
try {
  return user.profile.preferences.theme;
} catch (e) {
  return null; // Masks missing user or profile object
}

// ✅ Surgical Verified Patch:
// In src/services/user-preference.ts
export function getUserTheme(user: User | null | undefined): Theme {
  if (!user?.profile?.preferences?.theme) {
    return DEFAULT_THEME;
  }
  return user.profile.preferences.theme;
}
```

### Pattern B: Async Race Condition & Concurrent Mutex
**Problem:** Multiple concurrent calls update shared cache without synchronization, leading to race condition.
```go
// ❌ Flawed / Anti-pattern Patch:
// Adding time.Sleep(10 * time.Millisecond) hoping the race resolves

// ✅ Surgical Verified Patch:
type SafeCache struct {
    mu    sync.RWMutex
    store map[string][]byte
}

func (c *SafeCache) Set(key string, val []byte) {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.store[key] = val
}

func (c *SafeCache) Get(key string) ([]byte, bool) {
    c.mu.RLock()
    defer c.mu.RUnlock()
    val, ok := c.store[key]
    return val, ok
}
```

### Pattern C: Resource Leak on Exception
**Problem:** Database connection or file handle remains open if an exception occurs mid-operation.
```python
# ❌ Flawed / Anti-pattern Patch:
f = open("data.bin", "rb")
data = f.read()
process(data)
f.close() # Never reached if process() throws!

# ✅ Surgical Verified Patch:
with open("data.bin", "rb") as f:
    data = f.read()
    process(data)
```

## 6. Automated Verification Shell Commands

### JavaScript / TypeScript Workflows
```powershell
# 1. Run target regression test
npm test -- -t "should safely handle missing user profile preferences"

# 2. Run full test suite with bail-on-failure
npm test -- --bail

# 3. Type check & linter
npx tsc --noEmit
npm run lint
```

### Python Workflows
```powershell
# 1. Run targeted regression test
pytest -k "test_user_profile_missing_preferences" -v

# 2. Run full pytest suite with early exit
pytest -x --maxfail=1

# 3. Type check and code style
mypy src/
ruff check .
```

### Go Workflows
```powershell
# 1. Run targeted test with race detector
go test -race -v -run TestUserProfilePreferences ./pkg/...

# 2. Run full test suite
go test -race ./...

# 3. Static check
golangci-lint run
```

## 7. Rollback & Mitigation Strategies

If a verification step fails during patch validation:
1. **Never Compound Edits:** Do not pile speculative secondary patches on top of an unverified primary patch.
2. **Revert Immediately:** Revert to the clean git worktree state (`git checkout -- <file>` or discard edits).
3. **Re-evaluate Root Cause:** Return to the Root Cause Analysis (RCA) protocol to determine where the hypothesis was flawed.
4. **Document Finding:** Record why the hypothesis failed (e.g., hidden side-effect in downstream dependency) to guide the next iteration.
